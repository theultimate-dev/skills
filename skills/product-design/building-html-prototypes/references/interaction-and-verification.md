# Interaction and verification

## Build the smallest meaningful interaction

Choose native controls first. A button performs an action; a link navigates. Inputs need visible labels. A custom role does not supply keyboard behavior; consult the relevant [WAI-ARIA guidance](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/) only for a widget the task actually requires.

Keep focus where the user's task continues. Filtering normally updates the list without moving focus. If an action hides or removes the focused control, move focus to an appropriate remaining control. Announce short dynamic results politely; do not turn the entire result list into a repeatedly read live region.

Simulate asynchronous states only when exploring that future behavior. Do not add spinners to an immediate local filter. Use explicit local sample data, preserve input on errors, and give useful recovery for empty results.

## Verification sequence

1. **Static portability:** inspect HTML, CSS URLs, scripts, and embedded assets for remote or sibling dependencies, imports, requests, form submissions, and external SVG references. Check inline script syntax. For a design tree, run the design-tree check from the [design-tree contract](design-tree-contract.md#check-the-tree) instead of following references by hand; sibling files inside the tree are expected, and the check reports any reference that leaves it. Still read each script for requests and imports.
2. **Direct opening:** open the file itself, not a development server; in a design tree, open each page from its place in the tree. Block/disconnect the network and reload. Check for failed resource requests and script errors with available browser tools. Browser background traffic is distinct from document requests.
3. **Hosted render:** when reviewers will open the artifact through a host, such as a review site or an artifact viewer, also check it served, and keep the direct-opening result. This local check is required for a design tree; a one-file artifact has no relative paths to break, so it is optional there. Stage the exact file set under the nested prefix `/a/b/`, as [Serve files locally](#serve-files-locally) describes, with the [entry page](design-tree-contract.md#publish-through-an-entry-page) at the tree's root. Run the design-tree check on that stage. Then repeat the render check from direct opening, this time over HTTP: load the entry page in the [interaction harness](scripted-checks.md#the-interaction-harness), follow it to each view, and assert that the view renders with its shared styles, for example by reading a token's computed value with `style(':root', '--<token>')`. Record the result in the notes' row for the hosted render under a nested prefix. The local server stands in for a path prefix and a single entry page, not for the host's other rules, so the render on the host itself has a row of its own. When you cannot open the host, record that row as "not performed", and ask the user to open the published entry page and confirm that each view renders with its shared styles. Record their answer in the same row; until they answer, it stays "not performed". When they report a view without its styles, compare how the host published the tree with the entry-page rules.
4. **Task behavior:** exercise the primary journey and relevant recovery states. Confirm counts, labels, results, return actions, and simulations behave as described. Exercise every stateful interaction, such as open and close, timers, and focus return: drive it with a browser-driving tool when one can, and otherwise write a [scripted check](scripted-checks.md) for it.
5. **Input:** complete the task using keyboard alone, with visible focus and appropriate reading order. A scripted check covers key handlers such as Escape; real Tab order needs a browser-driving tool or a manual pass. Check pointer/touch-relevant controls do not require hover. If announcing dynamic results matters, inspect semantics and use assistive technology when available; DOM inspection alone does not verify spoken output.
6. **Layout:** inspect a narrow viewport around 320 CSS pixels and a representative wide viewport; when a headless browser will not narrow its window that far, use a frame of the exact width. Inspect a long page in [fixed-height slices](scripted-checks.md#long-pages-in-slices) rather than one full-page image. Test long titles, realistic paragraphs, and relevant missing content. Check wrapping, overlap, and unintended horizontal scrolling; genuinely two-dimensional content may need a different approach. See [W3C reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). A native surface drawn at a fixed scale, such as a desktop window or a watch face, follows the [native-surface profile](native-surface-profile.md) in place of the 320 px check for its scenes: the page around the scenes still reflows at 320 CSS pixels, and each scene scrolls inside its own container.
7. **Adaptation:** inspect at 200% text/page zoom and relevant reflow conditions. Override line height to 1.5, paragraph spacing to 2em, letter spacing to 0.12em, and word spacing to 0.16em without losing content or behavior. These are override checks, not required authored defaults; see [W3C text-spacing guidance](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).
8. **Visual and motion review:** check text/control contrast against the project's accessibility target, type hierarchy, measure, grouping, and density. If animation exists, honor reduced-motion preferences and ensure understanding does not depend on animation.

Use the browser tooling available; no particular automation library is required. When the only browser is headless, the [scripted checks](scripted-checks.md) exercise interactions and inspect narrow and long pages. Record exact checks performed, each scripted or driven check by name, and limitations. A file can pass static checks and still render poorly. Do not claim conformance to an accessibility standard based on a prototype checklist.

## Serve files locally

Some checks run over HTTP, because a browser treats each `file://` document as an opaque origin and blocks the reads and frames a check needs ([MDN, Same-origin policy: File origins](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#file_origins)). Stage the files the same way for every such check:

1. Create an empty staging folder outside the project. Copy the exact file set, untouched, to `<staging>/a/b/`. The nested prefix stands in for a host that serves the files under a path.
2. Copy each check template you use, such as `templates/tree-check.html`, to `<staging>/`, outside the tree, and fill in its inputs.
3. Serve `<staging>/` from the server root with any static file server bound to the local machine, for example `python3 -m http.server 8000 --bind 127.0.0.1` run in `<staging>/`.
4. Open `http://127.0.0.1:<port>/<template>` and read its results. Stop the server and delete the staging folder when the checks are done.

Every check template writes its results into one element, `#results`, one line per check: `PASS <name>`, or `FAIL <name>: <detail>`. The last line is `DONE <passed>/<total>`. Read the lines in the page, or from a DOM dump in a headless browser that lets the page's timers and requests finish first, for example Chrome's `--headless --virtual-time-budget=5000 --dump-dom <url>`. Without a `DONE` line the check has not finished, which is not a pass. Copy each check's name into the notes' verification table as it appears.

## Compare and refine

Inspect the same content and primary task in each sketch at the same viewport sizes. Describe observed differences and unresolved questions. After selection, repeat checks affected by revisions rather than rebuilding every alternative.

The delivered notes should distinguish completed checks, failures, and checks not performed. If browser access is unavailable, provide the manual steps above with the specific task actions and sample outcomes for that artifact.
