# Workflow and milestones

## Choose the next uncertainty

Start where the uncertainty is, not automatically at phase one. A supplied, approved brief can proceed to UX; a mature design system and a bounded feature may proceed directly from a flow to one prototype. A redesign can reopen visual choices without reopening an agreed product purpose.

| Phase | Develop | Evidence of completion |
|---|---|---|
| Frame | Audience, problem, outcomes, smallest useful scope, requirements and assumptions | User agrees what is being explored and what is excluded |
| Model | Information hierarchy, primary task, relevant states and recovery | Proposed behavior can be walked through without inventing major decisions |
| Diverge | Three direction briefs, then comparable offline HTML sketches | User can assess meaningful differences using the same task and content |
| Converge | Selected or explicitly combined direction, tokens, responsive behavior, key interactions | User's feedback is reflected in the refined prototype |
| Hand off | Traceability, acceptance criteria, limitations, suggested delivery slices | User agrees product/design readiness or remaining blockers are explicit |

UX questions that change product scope return to the scope decision. Direction selection follows HTML sketches, not merely verbal mood descriptions. Small type and spacing refinements can happen during convergence without a separate approval for every value.

## Three milestones

1. **Scope:** show the product brief, recommended smallest useful outcome, consequential assumptions, and alternatives where needed. Do not require a research report for a small feature.
2. **Direction:** show three standalone sketches, the same representative content/task in each, and a comparison of composition, type, rhythm, density, and usability. Explain the recommendation and ask which direction or specific combination to develop.
3. **Readiness:** show the refined prototype and handoff, highlight changed decisions, demonstrated behavior, and unresolved issues. Acceptance here is product/design agreement, not permission to deploy or proof of user validation.

If the user has explicitly delegated one of these decisions, make and record a recommendation under that delegation rather than introducing a fresh approval barrier. If a requested phase already has approval, reuse it.

## Minimum working memory

Record only what a fresh agent needs to continue:

- Outcome and scope; existing stack and relevant instruction sources, or lack of access.
- Preserve/evolve/replace choice and any approved exceptions.
- Current artifact locations and statuses; requirement identifiers if used.
- User decisions and their rationale, separated from proposed choices.
- Open questions with their consequences and whether they block the next phase.
- Next concrete action and the expected deliverable.

Do not create a parallel source of truth when the project already tracks this information. Update the existing brief or index instead. Prefer descriptive filenames; preserve old alternatives when replacing them would erase decision context.

## Research discipline

Inspect supplied and project materials first. Browse a small, relevant set of primary public sources when a proposal benefits from examples or verified technical facts. Record the source and the principle being adapted. Do not invent interviews, market statistics, or usability findings. If research is unavailable, mark the proposal as a hypothesis and suggest the smallest useful validation activity.

Exploration and convergence are informed by the Design Council's [Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/). Use the distinction to uncover and narrow possibilities, not to impose a fixed document ceremony.
